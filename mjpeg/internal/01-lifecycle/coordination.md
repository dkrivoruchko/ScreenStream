# Controller coordination

[MjpegStreamingModuleController](../../src/main/kotlin/io/screenstream/mjpeg/MjpegStreamingModuleController.kt) serializes commands and effective settings for one launch. It binds its Runtime, original Service, HTTP, address monitor and capture Access once; commands/reports never find a replacement. This page describes when the controller accepts work and reconciles its owners; linked pages define each owner's resource and algorithm contracts.

## Event loop and independent shutdown

The inert controller has a lazy Default event loop, a SupervisorJob and an unlimited event channel. `startModule` starts it only if Runtime is current, otherwise requests Shutdown. Settings/address/HTTP observations enqueue events; settings collection first performs the protected NewOnModuleStart PIN regeneration transaction. Address events retain the emitted monitor state, and processing the event advances the loop's address-state snapshot. HTTP events deduplicate server/consumer/fatal-cause changes rather than every statistics sample.

Only the loop mutates effective/latest-observed settings, selected-address facts, each attempt's processed capture state and address-loss episode, and slow-warning policy state. Each iteration reports processed uptime when due, checks LAN grant, calculates wait deadlines, handles one event, reads a fresh delivery snapshot, evaluates slow-viewer warnings, publishes UI and reports changed Status. A non-null HTTP fatal cause becomes a controller failure. Unexpected settings/discovery/delivery/loop failure reports manager failure and requests terminal Shutdown; an unexpectedly Closed/Failed monitor is not treated as recoverable discovery.

The one-second heartbeat wakes and runs in the real loop; the timer does not synthesize health. The next wait is the minimum of heartbeat and empty-selection deadline. Shutdown does not enqueue an event: it closes owner admission and begins independent cleanup even if the loop is blocked or never started. Ordinary enqueue ignores work after the terminal signal. Full shutdown mechanics belong to [Module lifecycle](module-lifecycle.md#controller-shutdown-and-complete-module-cleanup).

## Capture availability and command admission

The controller retains the latest admitted `CaptureAttempt`, including its session, processed state and optional address-loss episode, even after cleanup finishes. Availability is derived from the shutdown signal, accepted settings and that processed cleanup outcome. Shutdown overrides the other conditions below.

| Controller condition | Start/setup boundary | Current screen action |
| --- | --- | --- |
| Settings not accepted | Settings/configuration not yet established; LiveOnly | Busy after loop publication; initial UI is disabled Start. |
| Idle: settings accepted, shutdown not requested, and no attempt or processed cleanup succeeded | Setup edits allowed; Start also needs current listener readiness | Start enabled only when configuration/listener checks pass. |
| Active attempt: processed cleanup pending | Attempt owns consent through cleanup; LiveOnly | Stop after successful startup or in Suspended, otherwise Busy. |
| Processed cleanup failed | Last exact attempt retained; LiveOnly | Disabled Start. |
| Shutdown requested | No new work | Content is removed; no final UI reset is published. |

Action is advisory, not command authority. Start checks effective settings, derived idle availability and current available listener when handled. It creates a new attempt UUID, then enters the shared capture-admission gate to create a fresh generation, construct the inert session and attempt record, and register that exact attempt/generation with HTTP. Only accepted registration launches the session; Start retains the attempt record before leaving the gate. Shutdown cannot pass that gate and miss a new owner. Constructor failure therefore precedes HTTP registration, and rejected registration leaves no launched capture.

Stop checks the exact session ID in the retained attempt while its processed cleanup outcome is pending, requests the chosen reason and processes the latest capture session state; a stale attempt is ignored. Exact Stop can be handled during consent/startup/cleanup despite Busy. Retry delegates its server UUID to HTTP, which validates the current Failed incarnation. No command return confirms acceptance or completion.

CaptureChanged identifies an attempt but causes a fresh state read; event payload does not carry a second snapshot. New capture/cleanup failure references are logged/notified once as processed. Processing replaces the attempt's stored snapshot: null cleanup keeps it active, true permits idle availability, and false blocks Start. The attempt record remains retained in every case. The capture session owns phase/generation in its canonical snapshot and pushes committed changes directly to HTTP; processing a queued event cannot reopen or revoke production. Successful cleanup reapplies the latest observed preferences. Module status uses processed capture facts and fresh sampled HTTP consumer presence; its capture-attempt ID is cleared after successful cleanup and retained after failed cleanup until shutdown.

## Effective settings and saves

The controller retains the latest saved observation and effective settings: the values accepted under the current edit policy. Each observation derives a new accepted value. LiveOnly freezes backend, HTTP port and access settings other than `hidePinOnCaptureStart` from the previous effective value, while accepting image dynamics, filter, page, behavior and that PIN-visibility preference. This prevents late saved setup edits from changing a busy attempt. Exact schema/validation/write rules belong to [Settings](../02-configuration/settings.md).

Changed image values update the capture session's desired parameters. First settings acceptance starts discovery. Changed network values update the HTTP plan; an accepted filter change selects synchronously from the processed discovery inventory in the same turn. First settings acceptance permits derived idle availability; a completed loop turn with accepted settings has also applied initial HTTP configuration. Initial HTTP configuration reads the logo once on IO and transfers the bytes to HTTP; subsequent changes update access/page/image fallback. The HTTP change comparison excludes only `hidePinOnCaptureStart`, so changing that field alone neither updates HTTP configuration nor wakes JPEG readers. A rejected HTTP configuration is a module failure, not successful convergence.

PIN edits and regeneration use the Access settings group's ordinary save path. Typed edits validate six ASCII digits and the latest stored Permanent policy; regeneration works with either policy. The transaction checks the UI's current setup edit policy and writes through the shared settings mutex. Saving does not delay Start or form an atomic transaction with HTTP. A late saved restricted access change remains unapplied while capture is busy, then becomes eligible after successful cleanup. An admitted non-cancellable preference save may finish after the UI or module leaves.

Main-PIN visibility remains UI-local. With hiding enabled, entering or leaving an active attempt resets its reveal choice. Changing `hidePinOnCaptureStart` in either direction during consent, startup, capture or pending cleanup also resets a manually revealed PIN to hidden when the UI observes the applied change; turning it off never automatically reveals the PIN. Show remains available. After processed cleanup failure there is no active visibility flag, but the preference remains editable without unblocking Start. This uses current UI state, without controller event history or acknowledgement that a masked frame was rendered before capture.

With live `stopOnScreenOff` enabled, the controller owns a conditional subscription through consent, startup, active capture, reconfiguration and suspension. Its [AndroidScreenOffObserver](../../src/main/kotlin/io/screenstream/mjpeg/screenoff/AndroidScreenOffObserver.kt) uses the original Service Context, checks current interactivity before and after registration, and owns receiver registration and synchronous cleanup under one gate. The controller's callback captures the exact attempt and registration IDs; queued events are checked against both. Terminal shutdown closes the observer before its early-return guard, including synchronously before Service destruction returns. Device sleep requests exact-attempt System Stop; pending consent is cancelled and late results cannot restart it. Wake does not automatically start capture. Receiver registration failure rejects Start before admission or stops an existing attempt with Error when enabled live. HTTP lifetime and image fallback are unchanged by this preference.

## Keep screen awake

The controller applies `keepScreenAwake` immediately after accepting settings and when processing the exact capture attempt's state, before unrelated HTTP or notification work. `MjpegCaptureSession.updateScreenAwake` checks the saved choice against fresh `state.isStreaming` under its private wake-lock gate. Confirmed capture includes Reconfiguring and Suspended, independently of viewers or Activity visibility; consent, unconfirmed startup and HTTP-only operation are ineligible.

The session lazily retains one non-reference-counted `SCREEN_DIM_WAKE_LOCK`, created from its original Service Context with a stable tag and no wakeup flags. It acquires only when needed and not locally held, and releases otherwise. Stop publishes its sticky terminal state and releases under the same gate before cancelling outside it. JPEG-output failure, engine failure/stoppage and state-observation failure release before cancellation; outer finally releases again before media teardown. Fresh terminal state prevents a stale controller update from reacquiring. Power-operation exceptions only log; they do not change media failure/cleanup outcomes or show warnings.

The untimed request follows the user-controlled capture lifetime, with no heartbeat renewal. Android's [wake-lock guidance](https://developer.android.com/develop/background-work/background-tasks/awake/wakelock/set) demonstrates timed acquisition as a safeguard; an untimed lock avoids imposing an arbitrary duration or adding renewal machinery to a long capture. Explicit release still depends on runnable app threads and functioning Android calls. An ANR is not a release guarantee; process death removes the Binder-owned lock. Android can suppress screen effects while asleep or under applicable cached/frozen-process policies without updating the client's `isHeld`. Manual sleep remains effective, and this request never wakes or unlocks the device. Modern Android associates the request with the Service Context's display power group; it does not select the captured app's display.

## Slow-viewer warnings

The applied `notifySlowViewers` preference enables warnings only when the current capture session's fresh `state.value` reports confirmed streaming and `Active`. The controller uses the existing sampled `clients.isSlow` signal; [JPEG delivery](../03-delivery/jpeg-delivery.md#slow-reader-observations) owns its five-skipped-publication definition and limits. No warning-specific detector, timer, client identity or history is added. The existing one-second event-loop heartbeat observes HTTP statistics even when the HTTP collector suppresses a statistics-only change.

Three private controller fields own the policy. A nullable sample watermark is cleared while ineligible and set to elapsed realtime on entry; only strictly newer `sampledAtElapsedRealtimeMillis` values are accepted, and each accepted sample advances it. This rejects rows from before eligibility and duplicate snapshots. Any accepted sample with no slow rows clears the episode's notified latch. Otherwise an unnotified episode can request one warning when its sample timestamp is at least 30 seconds after the last completed Toast request. An episode that begins during cooldown remains unnotified and can warn on a later qualifying fresh sample. Multiple slow viewers share the same episode; uninterrupted slowness has no periodic reminder or recovery Toast.

The latch is set before the awaited main-thread Toast request, and the last-attempt time is recorded after it returns, including a handled platform failure. This module-lifetime cooldown survives reconnects, capture attempts and switch changes. Off, non-Active capture and shutdown clear the watermark and latch, without clearing cooldown. Resume or re-enable requires a sample newer than the next eligibility boundary.

The controller directly requests a standard `LENGTH_LONG` text Toast using the original Service Context on `Main.immediate`, checking coroutine cancellation and the captured session's fresh Active/streaming state plus shutdown immediately before the request. The main-thread block reads no mutable actor-owned settings. Cancellation propagates; ordinary platform failures are logged without failing capture. An already requested Toast expires naturally after Off or Stop. Android controls duration and may suppress or rate limit background Toasts; a request consumes the episode and cooldown regardless of visibility. No notification permission or channel is required. See [Android's Toast contract](https://developer.android.com/reference/android/widget/Toast).

## Discovery plan and Start readiness

The monitor publishes an immutable inventory containing all supported scoped IPs and their interface alternatives. The controller selects using `Observed.inventory.select(effectiveFilter)` from its processed address-state snapshot. An accepted filter change applies immediately without a monitor acknowledgement. While Loading it retains the last ready selection, and current permission immediately filters that retained plan. The controller passes the permitted address list and port to HTTP without retaining a second applied-plan cache. HTTP owns its last accepted ready plan and preserves unchanged server incarnations and responses; Start separately selects from the monitor's freshest inventory.

Start readiness requires open/current runtime, effective network settings, a fresh Observed inventory selected with the effective filter, a Listening server at the applied port, and matching address identity in both that fresh selection and the retained selected list. Both matching addresses must be eligible under the controller's current LAN grant evidence. This includes fresh interface metadata: a retained Mobile/VPN classification cannot admit Start after fresh evidence selects a Wi-Fi/Ethernet/Other interface requiring a denied grant. UI adds derived idle availability; accepted settings at loop publication also establish applied initial HTTP configuration. A stale visible listening row, arbitrary selected IP or successful HTTP activation alone cannot admit Start.

HTTP planned UUID and discovery address ID are independent. A grant change can remove/reintroduce a server with a new HTTP UUID/bind budget while preserving its discovery row. [Network addresses](../02-configuration/network-addresses.md) owns uncertain reads/identity; [HTTP delivery](../03-delivery/http-delivery.md) owns plan/incarnation/bind behavior.

## Network-loss deadline

Only an active attempt whose processed Observed inventory selects an **empty address list** under the effective filter starts an episode. Consent/startup/Active/Reconfiguring/Suspended can participate; Stopping/Stopped/Failed cannot. The episode is stored in that exact attempt's record, retains the effective filter and records elapsed realtime at first empty selection.

The configured timeout adds to that original time. Editing it does not restart loss. Any selected address, absent observation or terminal phase clears the episode; a changed attempt or effective filter starts a new interval if its selection is empty. Changing from one filter with an empty selection to another therefore restarts loss timing immediately. LAN denial or bind failure while selected addresses exist does not count as this loss. A timeout cannot start a later capture automatically.

At expiry, the controller rereads `addressMonitor.state.value` and selects from its inventory with the effective filter before exact System Stop. Recovery already published but still queued in the loop wins. An absent current observation or nonempty fresh selection clears the episode instead. [Module lifecycle](module-lifecycle.md#stop-and-suspension) owns Stop outcome; timeout never claims cleanup completed.

## LAN permission UI and grant checks

The SDK/target check requires `ACCESS_LOCAL_NETWORK` on SDK 37+ and target 37+. Each discovered address carries its permission requirement: non-loopback Wi-Fi/Ethernet/Other do, Mobile/VPN and loopback do not. These are module admission rules, not an assertion that every selected route is reachable; see [Android local-network protections](https://developer.android.com/privacy-and-security/local-network-permission).

[StreamAddressFailure](../../src/main/kotlin/io/screenstream/mjpeg/ui/main/StreamAddresses.kt) directly composes the zero-argument [LocalNetworkPermissionButton](../../src/main/kotlin/io/screenstream/mjpeg/ui/main/StreamAddresses.kt) only for PermissionDenied without an HTTP server ID. The private button reads `LocalRuntimePermissions` and collects LocalNetwork `PermissionState` itself. A fresh `isGranted(LocalNetwork)` check suppresses it when the OS grant is present; the last-known collected state supplies Requesting disablement and the SettingsSuggested label, without acting as grant authority or monitoring unrelated OS changes. Only its onClick calls `tryRequest(LocalNetwork)`. There is no automatic native LAN request, successful-admission flag, permission effect or request state in `MjpegContent` or the UI controller.

The button is private to `StreamAddresses.kt`. Its full-width tonal layout sits below the four address actions: red shield, Request permission/Open settings label, smaller explanation and centered action icon. It uses a neutral themed surface, native rounded shape and RTL-mirrored icons. The Settings action still requires confirmation in the shared app root. SettingsSuggested is a rationale/history heuristic, not proof of permanent denial. A platform-denied bind with an existing server ID keeps server Retry instead of the missing-grant action. Address rows compose the concrete button directly, without a passed button slot or permission DTO.

The controller's heartbeat reads `RuntimePermission.LocalNetwork.isGranted(service)`, whose shared implementation owns the SDK/target guard and fresh `checkSelfPermission` read. This independently governs permission filtering of the HTTP plan and capture readiness, including the matching fresh address's metadata at Start. UI state and `tryRequest` admission do not authorize the plan. Denial preserves filter settings/address rows and excludes only addresses requiring grant from HTTP. A fresh grant updates eligible listeners without automatic capture Start. Once admitted by the app, the prompt is independent of leaving or replacing the originating screen. [Streaming host](streaming-host.md#ordinary-runtime-permissions) owns that app slot; native MJPEG stores no permission history or education-completed preference.

## Native state projection and current UI

[MjpegUiController](../../src/main/kotlin/io/screenstream/mjpeg/ui/MjpegUiController.kt) maps local screen facts directly into its UI StateFlow and forwards capture commands to the original loop. The app observes manager state and owns all generic recovery UI between the module selector and retained module content, with Restart routed directly to the manager. Collection does not start HTTP/capture or own streaming resources. Content uses the actual remaining module width and height after the host layout. A scrolling staggered grid uses one column below 800dp and two columns from 800dp, with a reserved action footer; it inherits the host theme and consumed insets.

Native UI state includes ready Action, handled suspension problem, selected address rows, current edit policy and applied protected PIN. Generic diagnostics go only through `Status.errorMessage`: null means no local warning; otherwise the controller supplies the retained capture/cleanup or screen-off failure's trimmed nonblank exception message, falling back to its stage or cause class. With no actual failure, delayed Stop supplies the untranslated text `Capture cleanup is still pending`. There is no synthetic failure or native recovery-UI state. Host responsiveness stays in manager state. The mapper in [MjpegUiController](../../src/main/kotlin/io/screenstream/mjpeg/ui/MjpegUiController.kt) maps rows using discovery ID plus applied port and translates listener failure. Missing required permission yields PermissionDenied with no HTTP server UUID, Retry or applied viewing link. Portable applied links require Listening, permission and applied access; IPv6 scope is removed and link/site-local IPv6 URLs are excluded. Address actions remain available with a plain HTTP endpoint fallback. HTTP Info and applied access token remain separate reads, not a global transaction.

The host warning uses one generic localized heading, optional untranslated diagnostic text, and Restart module. Actual failures remain visible through rejected, canceled or failed capture Start and when leaving/reopening the screen. Confirmed successful capture startup clears the previous error, as does module replacement; ordinary Start/Stop admission is unchanged. The attempt snapshots the existing failure reference before startup. On the processed `startSucceeded` false-to-true transition, the controller clears only that unchanged previous error, before reporting fresh failures in the same turn; a newer screen-off or session failure survives even if it was reported before the startup transition was processed. One timestamp on the capture-attempt record tracks pending Stop. The existing heartbeat derives a warning after three seconds until the controller processes cleanup: fresh successful cleanup suppresses it immediately, while a fresh failed outcome keeps it until the retained failure is projected, avoiding a false resolved interval. This transient warning disappears after cleanup processing unless an actual local failure remains. The deadline does not cancel, complete or add a wait to cleanup. UI and notifications consume the same manager status; [Streaming host](streaming-host.md#original-service-and-foreground-obligations) defines warning episodes and terminal-failure delivery.

[MjpegContent](../../src/main/kotlin/io/screenstream/mjpeg/ui/MjpegContent.kt) composes stream addresses, five separate collapsible settings groups, suspension reasons and a reserved bottom Start/Busy/Stop control. [Stream addresses](../../src/main/kotlin/io/screenstream/mjpeg/ui/main/StreamAddresses.kt) uses each supplied address snapshot and its available viewing link or plain HTTP endpoint for Copy/Open/Share/QR. Copy marks the clipboard sensitive. Row-owned QR state is transient and resets when its URL changes or the row leaves composition. The shared applied-PIN row below the addresses starts masked and offers Show/Hide and sensitive Copy PIN during capture. Its single hint explains that access links and their QR codes open without a PIN, while typing an address requires PIN entry. Access settings retain separate masked saved-PIN controls; credentials and reveal state are not saveable. Stop rereads the displayed action and exact attempt. Permission state is collected only by the concrete permission button where that row is composed; `MjpegContent` has no permission handling, and the Activity root owns the platform launcher.

[Settings](../02-configuration/settings.md#native-settings-controls) provide five searchable groups with anchored choice menus, numeric and appearance forms, main-list switches and PIN controls. Forms save a changed valid draft on dismissal; list switches and exclusive menu selections save immediately. Group edits use the singleton's generic `updateData` transactions, ordered at its mutex and transformed from the latest stored snapshot; invalid text stays local and does not replace saved choices. The [network-filter editor](../../src/main/kotlin/io/screenstream/mjpeg/ui/settings/connection/NetworkFilter.kt) preserves nonempty groups and changes only the filter in the latest network settings. Forms use a sheet or dialog according to the native window width. PIN edits and regeneration share that group save path and its existing access-settings Snackbar error.

Public UI state is valid only while the manager admits the original instance. Shutdown cancels the controller job without a final Busy reset. The manager removes content when admission ends, and admission checks reject stale actions. The screen has no preview, viewer/statistics presentation or capture Retry action.
